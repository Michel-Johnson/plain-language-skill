# 详细表达原则

仅在长文、高风险或技术密集任务中读取。

## 先定内容与结构

先在内部确定读者、用途和主旨，再安排信息。读者需要作决定时补依据与取舍；需要执行时补前提、动作和失败处理。只补任务所需背景，不默认读者参与过项目，也不重复对话中已经交代的事实。

专业读者可直接使用熟悉术语；陌生术语才需就地解释。轻改或保留作者语气的任务，每次修改都应能指出具体理解障碍、错误或无信息的赘述。

## 大幅改写前列事实清单

| 项目 | 必须保留的内容 |
| --- | --- |
| 事实 | 名称、数字、单位、日期、版本、比较基线与来源 |
| 逻辑 | 因果、否定、条件、例外、不确定性与失败状态 |
| 责任 | 谁执行、谁受影响、时间顺序与责任归属 |
| 字面内容 | 代码、命令、路径、链接、标识符、JSON 键、API 名称及原样引用 |

用户只要求表达清楚时，不视为允许总结或删减。检查输出新增判断是否有依据，再检查必要事实是否完整保留。无法确认的原文歧义或疑似错误单独标注，不静默猜测或纠正。

## 逐句检查理解前提

按出现顺序检查专名、缩写、代词和条件是否已有解释或上下文依据。遇到缺口，优先补一句说明、改用明确名称，或标记待确认。以下例子只示范方法，具体数字和判断必须来自材料。

| 场景 | 原文或上下文 | 处理示例 |
| --- | --- | --- |
| 缺少术语解释 | 材料已定义 R3 是第三版路由规则；面向新同事写“R3 已启用” | “第三版路由规则（R3）已启用。” |
| 指代不明 | “解析器验证配置后交给执行器。它会记录错误。” | 先确认谁记录错误，不能擅自补成执行器 |
| 连续对话 | 上文已说明配置在部署失败时回滚；用户只问验证结果 | 直接报告实际结果，不重讲回滚背景 |
| 事实不足 | “新方案明显更快”，没有测量数据 | 保留判断强度并标注缺少测量，不编百分比 |

## 措辞与格式

用具体动作说明谁做什么；必要术语保留，同一概念不用多个近义词轮换。条件、例外和否定紧贴所约束的判断。按意思断句，长短服从逻辑关系。类比标明边界，例子不取代真实机制。

避免居高临下地称任务“很简单”或“显而易见”。标题、列表和表格按查找需要使用；保留用户要求的语气、语言、格式和链接。词表与长度提示用于复核，不能单独决定删词或改句。
